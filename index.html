“Test harness” is the engineering term for a rig that feeds prepared inputs into a system and reports what came back. It is a testing tool, not part of your product.

The short version of the job

  1. Work out which channel applies — DI (sales-tax invoices) or POS (retail receipts), or both. The comparison table is on the kit’s Overview tab.
  2. Get the sandbox token from IRIS. This is portal work, not code, and it takes days — start it before writing anything.
  3. Import FBR’s lookup lists (HS code, UoM, sale type, rate, SRO, province) onto your product and customer masters as dropdowns. Skipping this causes most production rejections.
  4. Prove the payload in the tester before wiring it into the application.
  5. Pass the assigned scenarios, get the production token, post one real low-value document, and verify it in IRIS.

Used by the tooling

  • fbr-di-sandbox-scenarios.json The 28 scenarios as ready-to-post request bodies. Already embedded in the kit page — take this file if you want them in Postman or your own tests.
  • fbr-proxy.js A ~60-line Node relay. The tester needs it, because a browser cannot call FBR directly (FBR sends no CORS headers). Run node fbr-proxy.js and leave it running.
  • harness.template.html  +  build-harness.js How the single page is produced. Edit the markdown, then run node build-harness.js to regenerate it. Nothing to install.
Before touching production: tokens are five-year credentials for a taxpayer’s identity — keep them server-side, never in a browser, a mobile binary, or git. And an invoice FBR has accepted cannot be edited or deleted, only reversed with a debit/credit note, so lock it in your database the moment FBR accepts it.
Sources: FBR Digital Invoicing API Technical Specification v1.12 and the POS Digital Invoicing technical specification, plus behaviour observed against the live sandbox. Confirm endpoint paths and IRIS menu labels against the spec issued with your own token — FBR moves them between releases.
